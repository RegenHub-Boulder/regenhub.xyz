# Newsletter delivery ledger (issue #97)

Migration: `053_newsletter_delivery.sql`. This release and migration are a coupled change. Do not deploy either with old newsletter workers running. Nothing in this change applies a migration or sends mail on its own.

## Delivery contract

Every newsletter delivery (admin or cron) uses one canonical `newsletter_issues.issue_key`, one database-owned revision and one `newsletter_sends` ledger. UI and MCP save via `newsletter_save_draft`; cron's `newsletter_ensure_week` inserts only when the weekly key does not exist. Cron preserves the autosend kill switch (including forced calls) and odd ISO-week cadence. The repository ships a concrete recurring scheduler in `ops/newsletter-scheduler.compose.yaml`: a sidecar using the built web image (already contains curl) calls the route again 60 seconds after each bounded request. Each call sends at most 20 recipients. The database's `cron_started_at` marker records ownership and `newsletter_cron_target` gives an eligible new weekly issue one initial turn before old continuation work. Subsequent turns rotate runnable issues by durable `cron_last_selected_at` (least recently selected first), so an issue that repeatedly fails cannot monopolize ticks. Runnable means an unprepared startup, a pending recipient whose database cooldown has expired, or an expired claim/sending lease needing cleanup. Fresh active leases and cooldown-only issues receive no turn; they remain durable and become discoverable again once ready, across day/week/year boundaries. A completed or waiting current Tuesday issue never blocks another runnable issue or triggers recompilation. A startup crash before audience preparation is also discoverable. New issues may start only on odd ISO-week Tuesdays in America/Denver (or an explicit authenticated force); ticks on other days only continue existing work. Completed weekly issues are skipped without recompilation. Unrelated manually prepared drafts and unknown-only issues are never automatically released. A call is resumable; an action-log entry is no longer a claim for the whole mailing.

All prepare, save, claim, begin, complete, retry, progress/finalize and resolution transactions lock the issue row. Delivery freezes the revision at the first recipient claim, just before the first possible external call. It is deliberately conservative: even a pre-I/O crash freezes the issue. The snapshot contains subject, body/rendered templates, version, site/archive origin, from and reply-to; its issue key comes from the database. A trigger rejects modification/deletion of a frozen revision, including draft upserts. Ledger writes and issue state writes are revoked from `service_role`, `authenticated` and `anon`; only the narrowly granted RPCs can mutate them. Thus old service-role workers fail closed. A database superuser can still bypass this operational boundary; do not use owner credentials for the application.

The claim is durable before any provider call. Each row carries an increasing fence and a two-minute lease. Only `pending` can be claimed. A **claimed** lease expires safely to pending because external I/O has not been authorized. `newsletter_begin` checks the current fence/lease and the unsubscribe table, persists the complete personalized provider payload, marks **sending**, and returns the provider key. Its transaction commits before the call. A missing/error/lost begin acknowledgement results in no external call. A sending lease expiry becomes **unknown**, increments the fence, and never returns to pending automatically. A stale completion cannot mark a row sent or overwrite its replacement.

Only a provider response with a message ID is counted sent. Explicit non-accepting 4xx rejections are failed (retry requires an operator action); explicit quota/rate rejections return to pending with a 1-hour/30-second cooldown. 408, 409, 5xx, transport errors, malformed responses and missing IDs are uncertain. They are quarantined. A provider acceptance followed by a lost acknowledgement, application crash or failed database completion stays sending until lease expiry, then unknown. No automated replay of unknowns exists, including within the provider retention window.

[Resend's official changelog](https://resend.com/changelog/idempotency-keys) documents **24-hour retention**, the same key and request parameters returning the same message ID, and Node's `emails.send(payload, { idempotencyKey })` signature. [Their engineering explanation](https://resend.com/blog/engineering-idempotency-keys) describes the key/payload binding. We pass this option as an additional safeguard, not as a perpetual exactly-once guarantee. Each authorized attempt has a fence-specific key; a new key is permitted only after proven rejection. On such a retry the exact stored personalized payload is reused, including unsubscribe URL, from/reply-to and all rendered content. Configuration/secret changes do not change that payload. Do not invalidate historical unsubscribe signing keys while recipients still need those links.

Unsubscribe is rechecked in the final database authorization step before each external call, and database errors fail closed. An opt-out arriving after that step can race the already authorized call; email and database cannot share a transaction. Other limitations: provider acceptance is not inbox delivery, an empty audience is not marked done, progress may contain terminal failures/skips while done, and unknown/active/pending always prevent done. No operator should interpret the issue's `sent` status as all recipients delivered; review the counts. Authored issue edits still require saving before sending; the server never trusts unsaved client content.

## Supervised migration and dry run

1. Turn off `NEWSLETTER_AUTOSEND_ENABLED`. Pause cron and admin send access. Drain **all** old web workers, running requests, queues/retries and MCP draft writers. A kill switch alone does not stop in-flight admin sends. Back up the database using the established operator procedure. Do not retrieve production data from a development workstation.
2. In the supervised database session, run `supabase/preflight/newsletter_delivery.sql` read-only. Confirm migration 052 is applied, 053 is the next filename, no unexpected ledger states/case-normalized duplicate addresses, and no privileged application clients outside service_role. Review counts of historical/in-flight issues and recipients; quarantine may require manual work. Preflight must report zero active workers through the operator's process/request inventory (SQL cannot prove this).
3. Rehearse in an isolated database restored by the operator. Apply 053 inside `BEGIN`, inspect the postflight counts below, then `ROLLBACK` for a dry run. Measure lock time on representative data; this migration scans the ledger and takes DDL locks. Perform the real apply in a supervised maintenance window, in one transaction through the existing migration ledger path; do not apply ad hoc SQL without recording migration/checksum.
4. Install the repository scheduler sidecar by merging `ops/newsletter-scheduler.compose.yaml` into the web service's Compose stack, using the same built image and network, supplying the existing cron token at runtime. Its default URL is `http://web:3000/api/cron/newsletter`; adjust that service name in configuration to the internal web service if necessary. Replace the old weekly-only scheduled task. Do not run both as the intended deployment configuration (overlapping calls are nevertheless fenced safely). No scheduler is deployed by this repository change. The repeated tick, not a user returning to the studio, is the continuation mechanism; keep the master flag off until the supervised checks finish.
5. Backfill is intentionally staged in the transaction before write restrictions and new functions. Existing sent/skipped rows keep their outcomes. Legacy failed rows and unfinished rows on any historical/ambiguous issue become unknown. Historical/in-flight issue revisions are frozen with a `legacy` marker: their original personalized requests are unavailable, so the new sender refuses to retry them. No historical row is reset to pending. Pristine draft pending rows with zero attempts and canonical lowercase/trimmed addresses remain eligible. Noncanonical legacy addresses quarantine their whole issue, preventing duplicate normalized addresses. They were prepared but have no evidence of sending.
6. Inspect `select status, count(*) from newsletter_sends group by status;` and `select count(*) from newsletter_issues where delivery_snapshot->>'legacy' = 'true';`. Confirm the audit table, trigger, execute grants and table write revocations. Start only the new web code. Exercise mocked/local delivery tests and read-only status. Restore admin access; enable cron only after review. Migration listing/checksum controls are unchanged.

## Resolve an unknown with evidence (never automatic)

1. Pause sending for the issue and drain all potentially active workers/provider requests before resolving anything. Identify row `id`, `issue_id`, current `fence`, `provider_key`, `call_started_at` and error in a supervised operator session. Keep this information private. Do not delete the ledger row or clear its payload/key.
2. Check provider dashboard/export/support records by recipient, time and key/ID. A missing dashboard search result alone is **not** proof of non-acceptance. Record a durable evidence reference and operator identity. If acceptance is confirmed, resolve sent with the provider message ID. If the provider establishes non-acceptance (or the row is known to have failed before I/O), resolve failed. If proof is unavailable, leave unknown or resolve skipped to close the issue without delivery; explicitly record that this sacrifices delivery to avoid duplicates. Legacy rows cannot safely reconstruct their original payload; mark accepted/skipped, and handle any proposed new mailing as a separate reviewed decision.
3. Execute `newsletter_resolve` in a supervised service-role/owner session, with the observed fence. Example using placeholders (do not paste without replacing evidence):

```sql
select newsletter_resolve(
  p_issue := 123, p_send := 456, p_fence := 7,
  p_outcome := 'sent', p_actor := 'operator-name',
  p_evidence := 'Provider export record/reference confirms acceptance for this attempt',
  p_provider_id := 'verified-provider-message-id'
);
select newsletter_progress(123);
```

`failed` permits an explicit `newsletter_retry_failed` action only after evidence review; unknown/active/sent/skipped are excluded. Resolution appends an audit record atomically and increments the fence. Completion, pre-I/O unsubscribe skips, and supervised resolution also refresh progress under the same issue lock and transaction, so a worker crash after the final recipient becomes terminal cannot strand the archive status or counters. Evidence and actor are required, with an ID required for sent. There is no UI button to blindly release unknowns. The studio displays active, unknown, skipped, failed and sent counts, and points uncertain recipients to this procedure.

## Rollback compatibility

Do not restore old binaries while this ledger is active. They do not understand claims, fences, unknowns, persisted payloads or frozen issues. Safest rollback is disable sending and retain the migration/data while fixing or reverting unrelated code. For an intentional full database rollback, first drain **all new and old** workers and external requests, preserve the ledger/audit/snapshots, and restore the supervised pre-migration backup with sending disabled. Reconcile every post-backup acceptance manually before ever resuming; restoring a backup can otherwise erase acceptance evidence and duplicate deliveries. Do not drop the constraints/columns or grant old table writes as a shortcut, and do not convert unknown/claimed/sending rows into pending for old-worker compatibility.
